# MW2 / XenDroid — knowledge sheet (read BEFORE any research, append AFTER)

Goal: MW2 (Xbox 360, title 41560817) on Poco X7 Pro (Dimensity 8400, Mali-G720 MC7, Arm r49p1, Android 16 / HyperOS 3). Target 60 fps native, less RAM/heat. Daily build: q140 + DELIVERY5 config.
Rule: every entry = fact + source/evidence + date. Mark [measured] (our phone), [verified] (2+ sources or code), [to verify].

## 1. Where the time goes (current, 2026-10-02)
- ~8000 draws/frame in gameplay; CpFastPath 94% of draws (our port of the peerloomllc "repeat draw" idea). [measured b165]
- fps ~44-45 (median), p10 ~39-42 with compressed textures, 720p swapchain. [measured b161/b165]
- Chain limit, not one saturated thread: CP thread ~77% on-CPU, guest threads ~50% idle; guest JIT = ~51% of app CPU. [measured b83/b139]
- mprotect write-watch cost 2.2-3.5 ms/frame on CP (86-116 calls, ~1600 pages). [measured b165]
- Heavy scenes: GPU exec ~22 ms/frame too (2026-09-28 note) — GPU and CPU both near the limit. [measured, old]
- RAM: GPU 1837 -> ~1300 MB (no fps loss); total PSS 2528 -> ~2250 (no ZC) / 1854 (zero-copy, -4 fps). [measured 10-02]

## 2. Tried — do NOT repeat (result)
- 13-GPR JIT allocator: 0.1-2% fewer insns, same ctx loads/stores -> no effect. [10-02]
- NaN fixups off: guest -7% ms/frame, fps same. jitlean vconst pool/fold/compact: ~1% insns. [10-02]
- async encoder thread, async swap, async submit 2 contexts: no fps gain. [10-02 and earlier]
- shm_unwatch_decay_frames=8, fault block 8 pages, pin threads, ADPF hint (-2 fps), Game Turbo not tested. [09-28/29]
- userfaultfd WP / PAGEMAP_SCAN / soft-dirty: not available on kernel 6.6 arm64 (uffd features 0x14ffe). [measured 10-01]
- Zero-copy AHB pipelined: -400 MB, fps 45 -> 37-41; black dots are NOT caused by it (they exist without ZC too). [10-02]
- Upload pool trim budget, 32 MB VMA blocks: no RAM gain. [10-02]
- Texture cache: shrinks only with short lifetime (soft 96 / lifetime 3 s); ASTC/EAC alone don't cut RAM because the cache refills. [10-02]
- PanVK G720 (wonderkast02 beta): users report slower than stock driver; not tried by us. [reddit 09-29/10-02]
- Frame generation: exists (internal), measured limits in internal notes (mw2-framegen-design).

### 2026-10-02 — mw2-recompiled + new CP work
- **mw2-recompiled renderer = Xenos PM4 emulation, not a D3D-level rewrite.** MW2 links D3D9 statically, so D3D9 runs as recompiled guest code and writes PM4 into a ring. The runtime's own command processor (`runtime/gpu/command_processor.cpp`, one ring-consumer thread) executes that stream: register file, IM_LOAD, DRAW_INDX, resolves, XE_SWAP. Xenos microcode goes to SPIR-V through its own translator and the Vulkan renderer is written for this one game. Why it matters: the CP bottleneck does not go away; the author says the consumer "holds the frame rate down" and driver calls were ~1/5 of its time. Source: https://github.com/PaulCombal/mw2-recompiled/blob/master/docs/d3d9-seam.md and docs/rendering.md (read 2026-10-02). [verified: official docs + source tree]
- **Not built on Xenia code, ReXGlue or UnleashedRecomp/plume.** The tree has its own `runtime/kernel` + `xam.cpp` HLE, its own `runtime/gpu`, SDL3 for window/input/audio, SIMDe via XenonRecomp, and a 31 KB XenonRecomp patch. Xenia is only a reference: formulas are ported (tiling, viewport, gamma, depth bias), the XMA decoder is a port of `xma_context_new.cc` + Xenia's FFmpeg branch, and the write-watch is "as Xenia does". ReXGlue is a separate Xenia-derived runtime (not used here). Sources: docs/runtime.md, docs/building.md, CMakeLists.txt, https://github.com/rexglue/rexglue-sdk (README, 2026-10-02). [verified]
- **MW2-specific shortcuts that make its renderer cheaper than generic Xenia (design ideas for our GPU/CP side).** (a) EDRAM is not emulated: one Vulkan image per surface keyed by {baseTile, pitch, format, samples}, because MW2 never aliases or tiles. (b) Only RT0 is bound; MRT is not implemented. (c) Resolves are image-to-image and never written back to guest RAM. (d) No vertex buffers: vertex windows are copied (or read from a 512 MB shadow of guest RAM) into one arena and fetched in the shader, with 3 descriptor sets and dynamic-offset uniforms. (e) Pipelines keyed by 2 shader hashes + formats + topology + blend + mask + samples; cull/depth/stencil are dynamic state. (f) A recorder thread queues the Vulkan calls (= our "async encoder": no fps gain for us). Why it matters: our ~30 render-pass breaks/frame and RT ownership transfers come from Xenia's generic EDRAM model; a title-specific "no aliasing" path could remove them. Source: docs/rendering.md. [verified that mw2-recompiled does it; benefit for XenDroid is [to verify]]
- **Write-watch is the same mprotect design as ours, with an adaptive back-off.** A page rewritten within 1024 frames of its copy waits 2^strikes frames (max 2^10) before it is re-armed or copied. We tried a flat `shm_unwatch_decay_frames=8` with no gain, so this exponential per-page version is not tested. Source: docs/rendering.md "The shadow of guest memory". [verified in docs; gain [to verify]]

- **Known ARM64 blockers/pitfalls for any XenonRecomp port.** (1) `sync`/`lwsync`/`eieio` generate no code in XenonRecomp (recompiler.cpp "no op"), which races on weakly ordered ARM; ReXGlue reported the same on 2026-09-30 (issue #462: "AArch64 hosts race"). (2) AArch64 FPCR exception bits are trap-enable (opposite polarity from MXCSR), so SIGFPE in guest code (ReXGlue #381, open). (3) Overlapping guest `memcpy` must be `memmove` on Android (UnleashedRecomp issue #1793, 2026-09-25, fixed in the Android port by PR #158). (4) BC1-5 textures need transcoding on Mali. (5) Memory: 4 GiB reservation, a double memfd mapping at 0xA0000000/0xC0000000, plus 512 MB arena and 512 MB shadow, which is heavy for our RAM goal. Sources: https://github.com/rexglue/rexglue-sdk/issues/462, /issues/381, https://github.com/hedge-dev/UnleashedRecomp/issues/1793. [verified for 1-3, 2 independent sources; 4-5 from docs]

## 2026-10-11 — Black Ops is latency-bound, not compute-bound (offline analysis of profile P3, q338, uncapped ~31 FPS)
Target (2026-10-11): 60 FPS at low temperature without the fan; 30 FPS is a fallback.
Tools (in `work/analysis/`): `attese.py <perf-report.txt.gz> [thread...]` (per thread: on-CPU time by category + off-CPU time by who called the sleep, exact durations from the context_switch records; needs `--trace-offcpu`), `catena.py` (pulse -> worker wake-up chain, idle sleep lengths), `core_per_thread.py` (which host cores each thread runs on, from `simpleperf dump`). Caveat: simpleperf's frame-pointer chains skip the direct caller of a leaf libc function and JIT frames have no callers, so "inclusive" JIT numbers are self times.
- 2026-10-11 — [measured, P3] Per 32 ms frame, the main thread (Guest CPU 5) runs ~10.4 ms of real game code and the render thread (Guest CPU 1) ~9.4 ms. The rest of both threads' frame is waiting: job-system loops (`sub_82545448`, `sub_82544D18`, `sub_82545BC8`, `sub_82544ED8`, `sub_825AF8F0` = 22-31% of their samples), NtWaitForSingleObjectEx polled at zero timeout (render 17% of its CPU, main 11%), NtYieldExecution (main 5%), scheduler/threading (4-8%), plus sleeps. Each of the two workers (Guest CPU 2/3) does only ~4.1 ms of real job work per frame, in ~79 wake-ups per frame (2460 idle sleeps/s each, median 80 us, p90 350 us): ~52 us of work per wake-up. => about 210 us of overhead per job batch; the frame time is made of hand-off latency. If hand-offs were free the critical path would be ~15-16 ms (60 FPS in reach).
- 2026-10-11 — [measured, P3] Where the hand-off latency is: (1) host `PosixEvent::Pulse` = Signal + `MaybeYield` (a WFE stall of up to 100 us on the 10 kHz event stream) + `Sleep(10us)` (43-70 us with timer slack) + Reset, about 100 us per pulse during which the pulser stands still, and `XEvent::Pulse` calls `WakeCooperativeWaiters()` only AFTER it, so the waiters start ~100 us late. Render thread: 781 pulses/s (25/frame), main 342/s (11/frame), Guest CPU 0: 8768/s (a pulse-only wait loop). (2) contention on `xe_global_mutex`: its slow path spins 128 tries (~1 us) then sleeps on the futex; main sleeps there 819 times/s (median 56 us, 8% of its wall time = 2.6 ms/frame), render 628/s (1.9 ms/frame). The "export:NtWaitForSingleObjectEx [syscall]" off-CPU entries are this futex (the only raw `syscall()` users are base/mutex.cc's futex and gettid). (3) the wake-up of an idle dispatch thread (futex wake + scheduler) on each of the ~79 kicks/frame per worker.
- 2026-10-11 — [reasoning from history] `pulse_event_skip_without_waiters` (q266, 7 Oct) and `global_mutex_spin_us` (b109, 2 Oct, MW2) were judged "no FPS gain" when the GPU was the limiter (BO 31 M GPU cycles/frame then; MW2 GPU-bound). ## 2026-10-11 night — long jumps (longjmp) in the ARM64 backend

- **How it works**: every translated function that makes calls records on entry a "stack point" {host SP after the frame allocation, guest r1 at entry (= the caller's), guest LR}. A `blr` to an address other than the expected return goes through the indirection table; if the address is not there it reaches `ResolveFunction`, which recognizes a return point inside an already compiled function and arms the synchronization (`pending_stackpoint_sync_depth`); the code after each call checks it and the helper restores host SP and depth.
- **Bug found (inherited from the port)**: the search stopped at the stack point with entry r1 equal to the restored r1, which is the function *called* by the target, and restored its host SP: the target continued on the wrong frame. On x64 the same search is correct because there the stack point is recorded *before* allocating the frame. Moreover, jumps over 1-2 frames were not treated as such: the return point was compiled as a function of its own, entered the indirection table, and from then on no jump to that point went through the synchronization anymore (stack leak on every jump).
- **Correct rule** (`a64_longjmp_target_frame`): target = first stack point from the top with entry r1 strictly greater than the restored r1; at least one frame above; the frame immediately above must have LR inside the target function.
- **Inlining of leaves**: a leaf with `mtlr` or `mflr` is not an ordinary leaf (longjmp/setjmp endings): never inline.
- **Tool**: `hostjit/build/longjmp [giri] [profondità]`. The bench loads the code into a module that the translator treats as a game module (`HostModule : XexModule`), so the return points are marked as on the phone.
- **Not verified**: which games really use longjmp and how often; no evidence on the phone.

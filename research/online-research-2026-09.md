## 2026-09-28 23:44 — Topic 2 (push descriptors / descriptor buffer / Mali-G720 descriptor cost), Topic 1 (Xenia forks, CP performance), Topic 3 (PanVK G720, marginal)

- **Push descriptors are core in Vulkan 1.4, and Arm's proprietary driver passed Vulkan 1.4 CTS for Mali-G720, Immortalis-G720, Mali-G715, Immortalis-G715** (submissions 922/923/925/926, 2025-06-06, CTS 1.4.1.2; run on Debian Linux, not Android). Why: any 1.4 Arm DDK must expose VK_KHR_push_descriptor. But our phone has r49p1 (MediaTek-customized, older than the June 2025 conformance run), so it is not guaranteed to expose 1.4 or the extension. Action for us: read `apiVersion` and the extension list (VK_KHR_push_descriptor, VK_EXT_descriptor_buffer, VK_EXT_shader_object, VK_KHR_dynamic_rendering) from the XenDroid Vulkan init log or `vkEnumerateDeviceExtensionProperties`. Sources: https://www.khronos.org/conformance/adopters/conformant-products/vulkan (official, fetched 2026-09-28); https://www.khronos.org/news/press/khronos-streamlines-development-and-deployment-of-gpu-accelerated-applications-with-vulkan-1.4 (official, 2024-12-03). **[verified: push descriptor in core 1.4 and G720 1.4 conformance; NOT verified for r49p1 on this phone]**

- **VK_EXT_descriptor_buffer on Mali-G720 with Arm's Android driver: no public evidence found either way.** vulkan.gpuinfo.org pages (Mali-G720-Immortalis filters) returned empty tables through the fetch tool (probably JS-rendered), so this is inconclusive, not a "no". Arm's public best-practice material (Vulkanised 2025 slides, Arm GPU Best Practices 3.4) only covers render passes, barriers, descriptor caching, and does not mention descriptor buffer or push descriptor cost. Why: do not plan work around descriptor_buffer on Mali until the device query above confirms it. Sources: https://vulkan.gpuinfo.org/listreports.php?devicename=Mali-G720-Immortalis&platform=android&extension=VK_EXT_descriptor_buffer (empty render); https://vulkan.org/user/pages/09.events/vulkanised-2025/T18-Pete-Harris-Arm-MobileBestPractices.pdf (2025-02). **[to verify]**

- **Arm's own guidance: descriptor updates are the CPU hot spot; the cure is to reuse descriptor sets (hash-map cache) and use dynamic offsets into one big per-frame buffer.** Their sample: 44 ms -> 27 ms (-38%) on a 2019 phone when caching sets; update time can exceed the draw time. Also: Arm says push constants have no advantage over UBOs on Arm GPUs (relevant to any "move X to push constant" idea: it saves descriptor/constant-buffer rewrites, not GPU work). No published numbers for push descriptors or update templates on Mali. Sources: https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/vulkan-descriptor-and-buffer-management (2019-11-12); https://docs.vulkan.org/samples/latest/samples/performance/descriptor_management/README.html; https://github.com/azhirnov/cpu-gpu-arch/blob/main/gpu/ARM-Mali_Guide.md (third-party summary). **[verified: 2019 Arm blog + Khronos sample agree; old, not G720-specific]**

- **A Xenia-canary fork (peerloomllc, branch linux-native-work) merged on 2026-09-27 a CP-thread-bound fix that is very close to our symptom.** Blue Dragon, ~13,700 draws/frame of 3 indices each, CP thread at 100%: 30.5 fps -> 45 fps with texture descriptor set reuse (skip rewrite while images/samplers/layout match in the same submission) + VGT_INDX_OFFSET moved from system constant to a vertex push constant + deferred tessellation constant invalidation; -> 60 fps with a new fast path `TryFastRepeatDraw` (cvar `fast_repeat_draws`, default on) that, when a draw differs from the previous eligible one only by index offset, skips the whole per-draw setup (no state/descriptor/constants rebuild) and issues the draw with firstIndex + pushed offset. Eligibility: same primitive type, index count, shaders, pipeline, submission, no texture-cache invalidation, all vfetch ranges still resident. Not Android, desktop Linux, but the CP-bound logic is API-side and portable. Source: https://github.com/peerloomllc/xenia-canary/pull/53 and https://patch-diff.githubusercontent.com/raw/peerloomllc/xenia-canary/pull/53.diff (2026-09-27, merged). **[to verify as applicable to MW2: single source, single title tested; the mechanism is verified from the diff]**

- **Cross-check against our local source** (src/xendroid-src/.../gpu/vulkan/vulkan_command_processor.cc): we already have texture descriptor set reuse (hash gate and `vulkan_texture_descriptor_reuse_edge` gate, lines ~8925-9000) and a dynamic-offset skip-rewrite path for constants. What we do NOT have: `vertex_base_index` is still a system constant (line ~8029, `dirty |= system_constants_.vertex_base_index != vgt_indx_offset`), so every distinct VGT_INDX_OFFSET dirties the constants and forces a new constants set; and there is no repeat-draw fast path. Whether it pays off for MW2 depends on how many consecutive draws differ only by index offset (unknown). Cheap experiment: count, per frame, draws whose full state hash equals the previous draw except vertex_base_index. If it is a large fraction of the ~7000 draws, port the push-constant + fast path idea; if not, skip. Source: local code read, no web. **[verified locally; benefit for MW2 unknown]**

## 2026-09-29 00:35 — Topic 4 (thermal / Game Turbo), Topic 5 (per-draw tricks from other emulators), plus shared-memory RequestRange caching (new CP context)

- **Upstream canary `SharedMemory::RequestRange` = bitset page check + global critical region; no per-submission memo.** Early exits (length 0, out of bounds), then `EnsureHostGpuMemoryAllocated`, then `TryFindUploadRange` under `global_critical_region_`; if no invalid page is found it returns true. Why: this is the baseline we diverged from. Our local `shared_memory.cc` (lines ~724-830) ALREADY has a lockless all-valid fast path, a hashed `request_cache_` keyed on (start,length) validated by `page_reads_generation_` and a global `valid_epoch_`, and the profile counters `stat_request_cache_hits_` / `stat_request_slow_`. So the remaining ~1 us/call is not the lock. Source: https://raw.githubusercontent.com/xenia-canary/xenia-canary/canary_experimental/src/xenia/gpu/shared_memory.cc (fetched 2026-09-29) + local code read. **[verified: code]**

- **Local analysis, not from the web: the likeliest reasons a call still costs ~1 us.** (a) `valid_epoch_` is GLOBAL: any invalidation of any page (the game rewriting a dynamic VB/constant page) bumps it and stales every cache entry, so hit rate may be low in a frame full of CPU-appended buffers; (b) misses go through `MarkRangeUsedInSubmission` (per-64-page-block flag updates, plus XXH3 of partial pages for tracked dynamic pages) which is much heavier than a hit; (c) with `log_cp_frame_breakdown` on, two `steady_clock::now()` per call are included in the measured 1 us. Cheap checks: print hits/slow/total per frame (the counters exist); measure with the timer off (count-only); if hit rate < ~70%, make the epoch per region (e.g. per 4 MB or per 64-block group) instead of global, so unrelated invalidations do not stale VB entries. **[to verify: needs the counters]**

- **Best fix is fewer calls, not faster calls: peerloomllc PR #53 hoists the global lock over all vfetch requests and skips setup for repeats.** `TryFastRepeatDraw` takes `global_critical_region` ONCE for the index-buffer + all vfetch `RequestRange` calls of a draw (stores `vfetch_addresses/sizes` of the previous eligible draw and replays them), and the full path in IssueDraw carries the comment "Pre-acquire the critical region so we're not repeatedly re-acquiring it in RequestRange". It still calls RequestRange per vfetch on the fast path, i.e. it does not memoize validity across draws; the win there is skipping descriptor/constants rebuild. Why: with ~14,600 requests/frame over ~7,000 draws (~2 per draw), a repeat-draw path that skips the requests entirely when (same submission, same vfetch addresses/sizes as the previous draw, `valid_epoch_` unchanged since the previous draw) would remove most of the 15 ms. Sources: https://patch-diff.githubusercontent.com/raw/peerloomllc/xenia-canary/pull/53.diff (lines ~296-350, merged 2026-09-27); https://github.com/peerloomllc/xenia-canary/pulls (merged list, #53 2026-09-27, #54 2026-09-28, nothing else on CP/shared memory). **[verified: diff read; benefit for MW2 unknown]**

- **Xenia Edge / canary: no open or merged PR on shared-memory request batching or multi-threaded CP.** xenia-edge search for "shared memory" returns only #254 (A64 guest wait loops, open, 2026-08-27), #246 (POSIX helpers, closed) and #127 (ZPD rewrite, closed 2026-04-05). Why: nobody upstream is solving this; we are on our own (and PR #53 is the only close relative). Source: https://github.com/has207/xenia-edge/pulls?q=is%3Apr+shared+memory (2026-09-29). **[verified: repo listing]**

- **Other emulators do not validate per draw at all; they track at page granularity and only pay on change.** yuzu's buffer cache rewrite tracks CPU/GPU-modified state per page (4 KiB aligned buffers, flat 32 MiB-wide page table page->buffer), so a draw whose pages are unmodified costs a lookup, no upload; Eden keeps a `MemoryTracker` with the same idea (CPU writes mark dirty, GPU writes tracked as ranges). RPCS3 went the other way for cheap validity: PR #18243 revalidates a cached vertex range by comparing a 64-bit fingerprint of the first bytes (a u64 compare instead of hashing) after corruption reports. Why: our `valid` bitset is already the page-tracking design; the transferable trick is "make the check O(1) per range with a version stamp", which our epoch cache does, just too coarse (see above). The RPCS3 fingerprint is a fallback for ranges on pages that are "dynamic" (CPU-appended) instead of hashing whole pages. Sources: https://yuzu-emu.org/entry/yuzu-bcr/ (search summary, page fetch failed); https://deepwiki.com/eden-emulator/mirror/3.5-texture-cache-and-buffer-cache ; https://github.com/RPCS3/rpcs3/pull/18243 (fetched). **[to verify for yuzu/Eden: secondary summaries only; RPCS3 PR verified]**

- **RPCS3 stated goal: vertex/index buffer caching "brings huge gains because backends spend several ms uploading buffers that barely change between frames".** Not measured for us (we do not upload vertex data per draw; the buffers are in the 512 MB shared buffer), so this confirms our cost is validation bookkeeping, not copies. No numbers or 2026 PRs found. Source: https://github.com/RPCS3/rpcs3/issues/1631 (search summary). **[to verify: summary only]**

- **Reviews show the X7 Pro holds ~73% CPU / ~77% GPU in long stress runs (3DMark stability 61-74% depending on test), so our observed drop (3.0-3.25 -> 1.4-2.0 GHz, ~45-60%) is worse than a normal stress test.** Likely causes: charging during the test (battery heat feeds the shared thermal zones), a case, and a workload that keeps all 8 cores plus GPU busy. Why: reproduce on battery at ~50-80% charge, no case, room-temperature start, possibly with a fan/cooler; if clocks then hold, thermals are an environment problem, not a hard cap. - **Official Android guidance: poll `PowerManager.getThermalHeadroom()` and cut load BEFORE severe throttling; a sustainable level beats oscillation.** Docs suggest lowering resolution/FPS or moving threads to smaller cores when the forecast (e.g. `getThermalHeadroom(30)`) approaches 1.0, then raising again. This is a different API from ADPF PerformanceHint (which cost ~10 ms per report on the CP thread): headroom polling can run on a background thread every few seconds, off the CP thread. Why: use it to auto-select a frame-limit/resolution-scale step (e.g. drop to 1.5x or cap 30 fps when headroom > 0.85) instead of letting the kernel cut the big cores to 1.4 GHz mid-frame; also useful just as a log column during tests. Sources: https://developer.android.com/games/optimize/adpf/thermal (official); https://source.android.com/docs/core/power/thermal-mitigation (official). **[verified: official docs; effectiveness on MT6899 unknown, forecast may return NaN]**

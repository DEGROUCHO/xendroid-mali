# Thermal / power / RAM research for XenDroid MW2 (D8400, Mali-G720) - 2026-09-30
Tags: [V] verified (fetched page or our own source code, link given). [S] seen only in a search snippet or a page summary; re-check. [H] hypothesis. Public hard data on this SoC is thin: no Geekerwan D8400 curve was retrievable, and emulator "heat guides" are SEO junk. Only app-side and adb-accessible methods are listed.

## 1) Ranked recommendations

1. **Measure first: build an fps-per-watt harness (section 3), then A/B three profiles.** Every other item below needs it.  Without it, "cooler" claims are just SoC temperatures, which the boost profile changes by itself.
2. **A/B the package profile: (a) a package the system treats as a benchmark, (b) original package added to Game Turbo with Performance mode, (c) original package, default.** Why it is hot: Xiaomi's thermal daemon has a "benchmark / no limits" profile (sconfig 6 = thermal-nolimits.conf, higher throttle triggers, uncapped CPU) and MIUI auto-selects profiles by detecting game or AnTuTu packages [S]. The 94-98 C is what "no limits" looks like, so the +20-40% fps is paid for with unthrottled power. Expected: (b) lands between (a) and (c) on both fps and heat; the winner is whoever has the best fps/W at a sustained 60 s. Test: read `adb shell cat /sys/class/thermal/thermal_message/sconfig` during each run (may be unreadable for shell on HyperOS 2; then infer from clocks and temps). Adding the app to Game Turbo is a manual UI toggle, not something that is scripted.
3. **Put the JIT guest threads on the 2.1 GHz cores, keep the command-processor (CP) and encoder threads on the fast cores.** The CP thread (75-80% busy) sets fps, so its clock matters linearly. The five guest threads are only 30-45% busy, so they are not the bottleneck and do not need 3.0+ GHz. Power rises faster than linearly with frequency at the top bins [H, standard DVFS physics; MediaTek claims 44% lower peak power than the Dimensity 8300, S]. Expected: same fps, lower package power; risk is guest latency on the frame-critical guest thread. The earlier "pin CP+encoder to 4-7" test only compared fps (44.5 vs 44.7), not watts. Test: verify topology with `cat /sys/devices/system/cpu/cpu*/cpufreq/cpuinfo_max_freq`, then A/B `gpu_threads_fast_cores` plus a new `guest_threads_slow_cores`, comparing mJ/frame.
4. **Extend DXT1->ASTC to DXT3/DXT5/DXN (BC2/3/5) and keep 4x4 blocks.** Mali has no BC, so today every non-DXT1 texture is RGBA8 (32 bpp) while ASTC 4x4 is 8 bpp. That is up to 4x less texture RAM and up to 4x less DRAM texture traffic, at unchanged block size (quality bounded by the validated transcode). DRAM traffic is a major GPU energy cost [Arm BP, V]. BC5/DXN can go to ETC2 EAC_RG11 (supported per the q79 log). Also set `VK_EXT_astc_decode_mode` = R8G8B8A8_UNORM on LDR ASTC views; the extension is exposed on r49p1 [V, gpuinfo report 47424]; the power benefit is [H].
5. **Cut duplicate RAM: the 512 MB shared-memory buffer.** [V, our code] `vulkan_shared_memory.cc` creates a full `kBufferSize` = 2^29 = 512 MB non-sparse buffer when sparse binding is missing (Mali), on top of the 512 MB guest physical mapping (memfd/ashmem in `memory_posix.cc`). That is about 1 GB for one guest RAM [H: that the driver commits all of it at allocation]. Measure with `dumpsys meminfo` (Graphics/EGL vs Native) and `/proc/<pid>/smaps_rollup`. Ideas: (i) cap the 240 MB pipeline cache by calling `vkGetPipelineCacheData` with a smaller buffer; the Arm driver then returns the highest-hit entries first [V, Arm BP 4.2]; (ii) long-term, zero-copy via AHardwareBuffer BLOB / dma-buf import (Mali has both, per internal notes) mapped at the fixed guest address. That would remove 512 MB and the 26% `UploadRanges` CP cost, but needs cache maintenance for non-coherent memory (the device exposes no cached+coherent type [V]) [H, high risk].
6. **Decide the cadence for lowest power: fixed guest 30 fps + 2x frame generation vs variable 40-45 native.** Heat scales roughly with work done; halving CP and guest work per presented frame is the largest single lever that keeps 60 presented [H]. Test mJ per presented frame for both.
7. **Give the vendor governor a steady frame target.** MediaTek's FPSGO-style governors key on frame timing [H]; call `ANativeWindow_setFrameRate(60, FIXED_SOURCE)` on the presenter and present at a fixed 60 Hz cadence (Swappy or GOOGLE_display_timing, both on r49p1 [V]). Also consider a 60 Hz display mode (`preferredDisplayModeId`): less SurfaceFlinger/display work at 120 Hz [H]. The ADPF hint test lost fps (42.9 vs 44.7), so do not rely on hint sessions.
8. **Look for guest spin loops.** PPC spin loops conventionally use `or r1,r1,r1` / `or r2,r2,r2` (thread-priority hint nops) [H that MW2 does]. If the JIT emits nothing for them, map them to ARM `yield` or a short backoff after N iterations. First check with simpleperf whether guest threads show hot tight loops.
9. **Arm GPU hygiene audit (energy via bandwidth):** verify AFBC is active on every RT with `VK_EXT_image_compression_control` (STORAGE usage or CREATE_ALIAS disables it [V]); resolve MSAA via `pResolveAttachments`, not `vkCmdResolveImage` (Arm: 3.9 GB/s vs 500 MB/s at 1080p60 4xMSAA) [V]; `DONT_CARE` loads/stores; merge barriers; compact samplers (LOD_CLAMP_NONE, no anisotropy) [V, all Arm BP].
10. **Non-software, legal:** a clip-on cooler. The benchmark profile tolerates 94-98 C, so cooling gives the same clocks at lower temperature. Hours at 42-44 C battery while charging also wear the battery; discharge during tests (section 3) removes that.

## 2) Short answers

**Q1 Benchmark vs game profiles.** [S] Xiaomi/MIUI switches thermal `sconfig` automatically per detected state (AnTuTu, games, camera); sconfig 6 = benchmark/unconstrained, 18-20 = game profiles (tgame, mgame, yuanshen). Sources: https://github.com/Inventor365/mi-thermal-tools, https://xdaforums.com/t/thermal-config-changer-for-pocophone-root.3886603/. Independent confirmation of the package trick: a fake app with AnTuTu's package name boosted a phone to max clocks and ignored thermal thresholds (Oppo F7 test) [S] https://www.gsmarena.com/oppo_caught_redhanded_once_again_with_its_f7-news-30837.php. No evidence was found of a documented package-to-game-profile trick on HyperOS; per-app mapping lives in the (encrypted) thermal files and Game Turbo's cloud list [H]. Manual route: Game Turbo > Add, then Performance mode [S] https://www.techbone.net/xiaomi/smartphone/add-games-or-apps-to-game-turbo, https://www.mi.com/global/support/article/KA-36416/. Android standard APIs: `android:appCategory="game"`/`isGame`, GameManager modes [S] https://developer.android.com/games/optimize/adpf/gamemode/gamemode-api; ADPF thermal headroom (0.0 none to 1.0 severe throttling, poll at most every 10 s, NaN if faster) [V] https://developer.android.com/games/optimize/adpf/thermal. MediaTek's MAGT claims 15-18% lower power in games but needs the game to integrate the SDK [S, vendor claim] https://www.mediatek.com/tek-talk-blogs/mediatek-and-google-collaborate-to-usher-in-a-new-era-of-smartphone-game-performance-tuning. `Window.setSustainedPerformanceMode` exists (Dolphin/PPSSPP discussed it) but the device must declare support [S] https://source.android.com/devices/tech/power/performance.html; test `PowerManager.isSustainedPerformanceModeSupported()`. It limits clocks, so it trades fps for heat.

**Q2 CPU efficiency.** No published D8400 perf/W curve found (Geekerwan reportedly calls it efficient at low/medium frequency, only a weak snippet, https://forums.anandtech.com/threads/mediatek-soc-thread.2614945/). MediaTek specs: 1x3.25, 3x3.0, 4x2.1 GHz A725 [S] https://www.mediatek.com/tek-talk-blogs/top-specs-of-the-dimensity-8400. App-side control is limited: `sched_setaffinity` works; clock caps do not without root. `sched_setattr` uclamp: the kernel doc says only EAS/CAS use uclamp [V] https://docs.kernel.org/scheduler/sched-util-clamp.html; the doc is silent on privilege, so whether an untrusted app may set it (seccomp/SELinux/CAP_SYS_NICE) is [H]; test one call, it costs minutes. Thread nice values via `setpriority` for the background encode/save threads are allowed. Frame caps reduce heat roughly in proportion to saved work only if the CP thread then idles (futex wait), not spins.

**Q3 Mali energy.** [V] Arm's best-practice guide (local copy read 2026-09-30): bandwidth is the lever (AFBC, transaction elimination, in-tile MSAA resolve, DONT_CARE, LAZILY_ALLOCATED transients), fewer than 1000 draws for Vulkan (we have ~7000), merge barriers, cache descriptor sets (38% frame-time cut in Arm's test), persistent mapping; fp16 gives ALU savings but changes quality, so skip it. https://developer.arm.com/documentation/101897/latest/ and https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/vulkan-descriptor-and-buffer-management. Device facts: https://vulkan.gpuinfo.org/displayreport.php?id=47424 (push_descriptor yes, descriptor_buffer/host_image_copy/external_memory_host no).

**Q4 Emulator tricks.** Little verifiable public data. [S] Eden/Skyline only claim ARM-specific tuning; NetherSX2 guides say charging while playing is the worst heat combination. A PPSSPP issue notes Dolphin implemented sustained-performance mode: https://github.com/hrydgard/ppsspp/issues/9738 [S]. Levers we already use: no spin waits, fastmem, fewer protection faults. For mprotect storms [H]: coalesce `mprotect` ranges, keep ring-buffer pages unwatched (q98), or try userfaultfd write-protect/soft-dirty polling.

**Q5 RAM.** Xenia models 4 GB guest virtual space plus 512 MB physical [S] https://www.mintlify.com/emoose/xenia/architecture/overview; the 4 GB is address-space reservation, cost is only what is touched [H]. No published Android RSS numbers found. Reductions: recommendations 4-5, plus a texture-cache budget cap and `madvise(MADV_DONTNEED)` on freed regions. Check `/proc/pressure/memory` and `pswpin/pswpout` in `/proc/vmstat` for zram/kswapd churn during a run.

## 3) How to measure power (fps per watt)

Problem: with USB charging, `current_now` is net of the charger and useless. [V] Battery counters cover the whole device, not per app; power rails (ODPM) exist on Pixel 6+ and many other phones lack them (https://perfetto.dev/docs/data-sources/battery-counters, https://developer.android.com/studio/profile/power-profiler). `current_now` paths and signs differ per device (https://hooo1941.github.io/2025/02/26/android_power/).

Recipe (discharge, 10-60 s runs, same brightness, same refresh rate, same SoC window, e.g. battery 60-80%):
1. `adb tcpip`/Wireless debugging (Android 11+), then unplug the cable. Keep the phone awake with a keep-awake loop, and confirm `dumpsys battery` shows `AC/USB powered: false`.
2. Sample at 1 Hz on the phone, not over adb round trips: `adb shell 'for i in $(seq 60); do echo $(date +%s) $(cat /sys/class/power_supply/battery/current_now) $(cat /sys/class/power_supply/battery/voltage_now); sleep 1; done' > pw.txt`. Units are usually uA and uV; discharge sign is device-specific (check at idle). W = |I|*V.
3. Same window: fps from the run logs, SoC zone temperatures, `scaling_cur_freq` of cpu0-7, GPU clock. Report `fps/W` and `mJ per presented frame` = W / fps * 1000, plus screen-on idle baseline (subtract it or report it).
4. Cross-check with Perfetto: config `android.power` with `battery_poll_ms: 250` and `collect_power_rails: true`; if the rails list is empty (likely on this SoC), ignore it.
5. If a cable is required, use an inline USB-C power meter at identical battery state; results are relative only. `dumpsys battery unplug` only fakes the state.
6. Also log CPU cycles per presented frame (simpleperf `cpu-cycles`): frequency-independent, good for code changes; watts are for profile/placement changes.
7. Run each variant 3x in alternating order from the same start temperature; compare medians; force-stop after each run.
